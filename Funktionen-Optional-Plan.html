Funktionen optional und einstellbar machen

Runback hat viele Funktionen. Nicht jeder will alle. Dieser Plan zeigt, was sich sinnvoll abschalten oder anpassen lässt, wie das im Produkt aussehen soll und in welcher Reihenfolge es gebaut wird.

Stand 18. September 2026 · Basis: Branch t3code/f0e795a7 nach PR #21 · Analyse von src/ui, src/domain, src/native.ts, docs/spec.md

Status: umgesetzt (19. September 2026) Alle vier Phasen sind in einem PR gebaut. Die offenen Entscheidungen wurden wie vorgeschlagen getroffen: Muskelkater-Abfrage standardmäßig „Nach Krafttraining“, Heute-Blöcke einzeln, Onboarding-Schritt „Was möchtest du nutzen?“. Zwischenzeitlich hat PR #24 die Navigation auf Heute · Plan · Verlauf · Coach umgestellt; die Umsetzung folgt dieser Struktur: Einstieg ist Einstellungen (Zahnrad) → Funktionen, die Heute-Blöcke sind Wochenleiste, Empfehlung, Muskelkater melden und Zuletzt, „Nur auf Nachfrage“ heißt: nur im Coach. Die Kennzahlen der Startkarte und der Zeitbudget-Schalter sind entfallen, weil die neue Startkarte keine Kennzahlen mehr trägt und Zeit & Rhythmus im Plan zusammengehören. Code: src/domain/features.ts, src/ui/FeatureSettings.tsx.

1. Warum das jetzt dran ist

Die Spec verspricht es bereits, die App löst es aber nur teilweise ein:

docs/spec.md → Mentalität „Alles ist optional. Aufzeichnen funktioniert ohne Ziel, Fokus, Plan, Einrichtung, Konto oder Internet. Jede Funktion ist abwählbar und erzeugt abgewählt weder Hinweise noch leere Flächen.“

Konkret sieht ein Nutzer heute auf Heute immer neun Blöcke, egal ob er sie nutzt: Startkarte, Deine Planung, Krafttraining, Dein Fokus, Dein Ziel, Empfehlung, Dein Körper, Zuletzt, Laufvorlagen. Wer nur läuft, sieht trotzdem „Freies Training starten“. Wer keinen Muskelkater melden will, bekommt beim ersten Öffnen jeden Tages die Muskelkater-Abfrage als Vollbild (RunbackApp.tsx:692–722) — ohne Möglichkeit, das abzustellen.

3. Vier Regeln für jede Option

1 · Aus heißt weg

Eine abgeschaltete Funktion verschwindet komplett: kein ausgegrauter Block, kein „aktiviere X, um …“, keine leere Sektion. Das ist die Spec-Regel und der Grund, warum es überhaupt Schalter braucht.

2 · Aus löscht nichts

Daten bleiben (Grundregel 1 und 10). Muskelkater aus → keine Abfrage, keine Karte; alte Meldungen bleiben in der Datenbank und im Backup. Wieder an → alles ist wieder da.

3 · Standard = heutiges Verhalten

Wer nichts anfasst, merkt nichts. Bestehende Nutzer sehen nach dem Update dieselbe App. Ausnahme nur nach expliziter Entscheidung (siehe Abschnitt 9).

4 · Ein Ort, klare Sprache

Alle Sichtbarkeits-Schalter auf einer Seite „Funktionen“. Verbindungen zu externen Diensten bleiben in „Geräte & Verbindungen“, weil dort Datenschutz erklärt wird. Kein Schalter erzeugt eine Grundregel-Verletzung.

Empfehlungen

Bedeutung

Sprache und Verhalten

  • Zeilentitel benennen die Funktion, nicht den Schalter: „Muskelkater melden“, nicht „Muskelkater-Tracking aktivieren“.
  • Der Untertitel zeigt den aktuellen Wert („Nach Krafttraining“, „6 von 8 sichtbar“), nie eine Erklärung.
  • Abschalten wirkt sofort, ohne Speichern-Knopf. Speichern läuft über das bestehende save() mit Fehleranzeige.
  • Ein Schalter, der etwas Laufendes betrifft (aktive Empfehlung, aktives Training), fragt einmal nach — mit dem bestehenden Alert-Muster wie beim Beenden eines Laufs.
  • Kein Schalter zeigt einen „Empfohlen“-Hinweis. Runback rät hier nicht.

Onboarding: ein Schritt mehr

Zwischen „Ziel“ und „Import“ kommt der Schritt „Was möchtest du nutzen?“ mit drei Kacheln: Laufen · Krafttraining · Radfahren (Mehrfachauswahl, Laufen vorausgewählt) und darunter der Schalter „Nach Muskelkater fragen“ mit der Häufigkeit. Alles überspringbar; Überspringen = alles an. Der Schritt schreibt nur features, sonst nichts.

7. Technischer Aufbau

Ein Modul, eine Version

Neu: src/domain/features.ts — reine Logik, ohne UI, mit Jest-Test daneben. Es kennt die Standardwerte, normalisiert Rohdaten aus settings.features und beantwortet Fragen wie „soll jetzt nach Muskelkater gefragt werden?“.

// src/domain/features.ts
export const FEATURES_VERSION = 1;

export type SorenessPrompt =
  | 'never' | 'after_strength' | 'daily' | 'training_days' | 'weekly';

export type RecommendationMode = 'suggest' | 'on_request' | 'off';

export interface FeatureSettings {
  version: typeof FEATURES_VERSION;
  areas: { running: boolean; strength: boolean };
  sports: { cycling: boolean };
  soreness: { enabled: boolean; prompt: SorenessPrompt; map: boolean; voice: boolean };
  home: { sections: HomeSection[] };
  planning: { enabled: boolean; suggest: boolean; month: boolean; budget: boolean };
  recommendations: {
    running: RecommendationMode; strength: RecommendationMode; showQueued: boolean;
  };
  recording: {
    metrics: RecordingMetric[]; primary: 'duration' | 'distance' | 'heartRate';
    targets: boolean; routes: boolean;
    afterRun: 'detail' | 'feeling' | 'home';
  };
  strength: { restTimer: boolean; defaultRestSeconds: number; rir: boolean; templateOfDay: boolean };
  statistics: { modules: StatsModule[] };
}

export const DEFAULT_FEATURES: FeatureSettings = { /* alles an = heutiges Verhalten */ };

/** Unbekannte oder fehlende Felder → Standard. Ungültige Werte → Standard. Nie werfen. */

8. Umsetzung in vier Phasen

Jede Phase ist ein eigener PR und für sich nützlich. Die Reihenfolge folgt dem Nutzen: zuerst das, was heute wirklich stört.

Fundament + Muskelkater + Bereiche P1
  • features.ts mit Version, Standardwerten, Normalisierung, Tests
  • Seite „Funktionen“ unter Mehr → Einstellungen (zunächst nur die Zeilen dieser Phase)
  • Muskelkater an/aus + Häufigkeit (fünf Modi); Auto-Abfrage nutzt shouldPromptSoreness

9. Offene Entscheidungen

Drei Punkte, bei denen es nicht nur eine richtige Antwort gibt. Alles andere im Plan ist so vorgeschlagen, dass es ohne Rückfrage gebaut werden kann.

#FrageOptionenVorschlag
1 Standard für „Wann nach Muskelkater fragen?“ a) Täglich — kein Verhaltenswechsel für bestehende Nutzer.
b) Nach Krafttraining — fachlich passender, seltener, und reine Läufer werden nie gefragt.		 b. Die tägliche Abfrage ist die häufigste Reibung. Wer sie will, schaltet zurück; die neue Seite ist beim ersten Start nach dem Update über eine einmalige Zeile auf Heute erreichbar („Neu: Du kannst wählen, was Runback zeigt“).
2 Heute-Blöcke: einzeln oder gebündelt? a) Acht einzelne Schalter.
b) Drei Bündel: „Kontext“ (Fokus, Ziel, Empfehlung), „Körper“, „Verlauf“ (Zuletzt, Vorlagen).		 a. Acht Zeilen auf einer Unterseite sind übersichtlich genug, und Bündel erzwingen Kompromisse („ich will Empfehlung, aber nicht Ziel“).
3 Onboarding-Schritt „Was möchtest du nutzen?“ — ja oder nein? a) Ja, ein Schritt mehr, überspringbar.
b) Nein, alles an; Nutzer findet die Seite unter Mehr.		 a. Ein Kraftsportler, der als Erstes eine Lauf-Startkarte sieht, ist verloren, bevor er „Mehr“ findet. Der Schritt ist eine Frage, keine Einrichtung.
